01

Resumo executivo

O Frotto hoje é composto por dois projetos independentes no mesmo repositório. frotto-server-main é um backend Java 17 + Spring Boot 2.7.3, originalmente gerado pelo JHipster (o pacote interno ainda se chama com.localuz) — apesar do package.json presente na raiz, ele é apenas um wrapper de scripts Maven, não uma aplicação Node.js. frotto-ui-main é uma SPA React 18 + Ionic React 6 em TypeScript, buildada com Create React App e servida por Nginx.

O backend expõe uma API REST em /api, autentica com JWT e persiste em MySQL via JPA/Hibernate, com schema versionado por Liquibase.

O ponto que mais importa para o roadmap de pagamentos

O modelo de dados é "um usuário dono de uma frota": cada carro pertence a exatamente um usuário, e tudo mais (motoristas, manutenções, despesas, pendências) é escopado a partir do carro. Não existe conceito de empresa, frota compartilhada ou múltiplos usuários acessando os mesmos veículos — e não existe, em nenhum lugar do código, qualquer conceito de plano, assinatura, premium ou limite de uso. A busca por essas palavras-chave no backend e no frontend deu zero resultados relevantes.

Dois achados de segurança são mais urgentes do que qualquer decisão de arquitetura de billing: o segredo de assinatura JWT está hardcoded em texto puro no repositório, idêntico entre dev e produção, e a validade do token tem um bug de unidade que o faz durar cerca de 1000 dias em vez das 24h pretendidas. Ambos ficam detalhados na seção 8.

Arquitetura atual

Uma SPA consome a API via axios, anexando o JWT em Authorization: Bearer. Em produção, dois domínios são roteados pelo Traefik para os respectivos containers.

06

Autenticação

1

Login

POST /api/authenticate — Spring Security valida usuário/senha com BCrypt.

2

Geração do token

TokenProvider assina um JWT em HS512. Sem refresh token — é um único JWT de longa duração.

3

Middleware

JWTFilter intercepta toda requisição e lê Authorization: Bearer <jwt>.

4

Identificação do usuário

SecurityContextHolder recebe login + roles — sem o id numérico. Endpoints filtram dados com ?#{principal.username} direto no JPQL; para obter o id é preciso UserService.getUserWithAuthorities().

5

Acesso aos endpoints

Tudo sob /api/** exige autenticação por padrão; /api/admin/** exige ROLE_ADMIN.

Relevante para relacionar assinatura ↔ usuário

Como o contexto de segurança carrega só o login, não o id, uma futura tabela subscriptions.user_id vai exigir esse carregamento explícito do User completo — não vem "de graça" do token.

Registro em POST /api/register (usuário criado desativado, ativa por e-mail); recuperação de senha em /api/account/reset-password/init e /finish. Senha armazenada com BCrypt confirmado.

08

Segurança

Crítico

Segredo de assinatura JWT hardcoded em texto puro em application-prod.yml, idêntico ao de dev (também hardcoded). Qualquer pessoa com acesso ao repositório pode forjar tokens válidos de produção — deve ser tratado como já comprometido e rotacionado para uma variável de ambiente.

Alto

Sem rate limiting em /api/authenticate e /api/register — exposto a brute-force/credential stuffing.

Bug de unidade na validade do JWT: comentário diz "24h", mas o valor está em segundos multiplicado por 1000 a mais (86.400.000s ≈ 1000 dias). Tokens duram muito mais do que o esperado.

CORS configurado em dois lugares divergentes (YAML via WebConfigurer vs. CorsConfig.java hardcoded) — um dos dois não libera PATCH, usado por vários endpoints.

debt_item_type não tem escopo por usuário nem exige ROLE_ADMIN — qualquer usuário autenticado pode criar/alterar/desativar itens dessa lista global.

Médio

.env e .env.production do frontend estão commitados no git (sem segredos reais identificados — só URLs e nome de bucket S3 — mas é má prática).

CORS de produção libera http://localhost mesmo no perfil prod.

application-prod.yml usa localhost como host de mail/logstash — parece default do JHipster nunca ajustado.

Isolamento por usuário depende de convenção manual (?#{principal.username} repetido em cada query) — um novo endpoint pode facilmente esquecer o filtro e vazar dados entre contas.

Baixo

Nenhum header de segurança customizado (CSP, HSTS) além do padrão do Spring Security.

Pontos positivos confirmados

Senha com BCrypt, sem SQL nativo/concatenado (tudo via JPA parametrizado), validação Bean Validation nas entidades, autenticação exigida por padrão em /api/**, nenhum log de senha/token encontrado.

Infraestrutura

Confirmado pelo código

  • Docker Compose na raiz define 2 serviços (backend, frontend), ambos atrás de Traefik (roteamento por Host()), sem HTTPS configurado no arquivo atual (entrypoint http nos dois).
  • Nginx serve o frontend estático e faz proxy de /api/ para o backend.
  • Backend empacotado como JAR Spring Boot, runtime Java 17 em Docker.
  • Existe config de AWS Elastic Beanstalk (.ebextensions) e uso de AWS S3 para arquivos.

Não foi possível confirmar

  • Provedor de hospedagem real (Hostinger, VPS específica, etc.) — sem referência textual no repositório.
  • Se o Elastic Beanstalk é o ambiente ativo hoje ou um resquício legado.
  • Pipeline de CI/CD — não existe .github/workflows.
  • Se o deploy é manual ou automatizado.
10

Situação atual para pagamentos

Precisa de ajustes — não é uma refatoração completa, mas também não está pronto para plugar billing hoje.

A base é sólida: separação clara controller/service/repository, JWT funcional, isolamento por usuário (mesmo que via convenção), schema versionado por Liquibase. Falta a peça central: não existe nenhum conceito de "conta que paga" — nem plano, nem multiusuário. O modelo atual (1 usuário = 1 frota) colide direto com a ideia de um plano "FROTAS" multiusuário. Os problemas de segurança crítico/alto da seção 08 deveriam ser corrigidos antes de vincular dinheiro real a uma sessão autenticada.

Checkout, webhooks e entitlements

  • Checkout externo: o modelo Frotto → backend → gateway → checkout hospedado pelo gateway é compatível com a arquitetura atual. O Frotto nunca precisa guardar número de cartão, CVV ou validade.
  • Webhooks: nova rota pública (/api/webhooks/{provider}), fora da exigência de JWT, validando a assinatura HMAC do provedor; eventos gravados em payment_events antes de aplicar qualquer mudança de status, para idempotência.
  • Entitlements (limites por plano): a validação não pode existir só no frontend. Um EntitlementService central, plugado nos controllers existentes (ex.: CarResource.createCarInternal), deve checar o limite do plano antes de qualquer criação — hoje não existe esse tipo de camada cruzando os controllers.

Alterações necessárias

Banco de dados

  • Criar plans, subscriptions, payment_events via changelog Liquibase.
  • Decidir e modelar "conta/empresa" se o plano multiusuário for adiante — hoje não existe, é a mudança estrutural mais profunda de todas.

Backend

  • Corrigir validade do JWT e mover o segredo para variável de ambiente (pré-requisito, não é billing em si).
  • Unificar a configuração de CORS hoje duplicada.
  • Rate limiting no login/registro.
  • EntitlementService central usado pelos controllers existentes.
  • Rota de webhook pública com verificação de assinatura, sem exigir JWT.

Frontend

  • Telas de plano/assinatura — greenfield, nada existe hoje.
  • Reaproveitar o padrão já existente (endpoints.ts + instância axios única).
  • Endurecer a anexação do token (hoje via axios.defaults.headers, não um interceptor) antes de mexer com pagamento.
  • Resolver a situação do Redux morto antes de decidir onde guardar o estado de assinatura.

Segurança

  • Rotacionar o segredo JWT.
  • Corrigir CORS e validade de token.
  • Middleware de idempotência/deduplicação para webhooks.

Infraestrutura

  • Definir e documentar o ambiente real de produção (hoje ambíguo entre Docker+Traefik e Elastic Beanstalk).
  • Configurar HTTPS de fato no Traefik.
  • Domínio/rota estável para receber webhooks dos gateways.
13

Riscos antes da implementação

01

Segredo JWT hardcoded e igual em dev/prod — corrigir antes de qualquer coisa envolvendo dinheiro.

02

Bug de validade do token (~1000 dias) — sessões não expiram como deveriam, problemático quando o acesso a features passa a depender do status de pagamento.

03

Ausência total de modelo de conta/empresa multiusuário — se o plano FROTAS depende disso, é a maior peça de trabalho de todo o roadmap, maior que o billing em si.

04

Isolamento de dados por convenção manual — arriscado replicar esse padrão nas tabelas de billing; melhor um mecanismo central.

05

.env do frontend commitado — trocar o processo antes de adicionar chave pública de gateway de pagamento ali.

06

Ambiente de produção real não está claramente documentado — o gateway de pagamento precisa de uma URL pública estável e confiável para o webhook.

07

Capacitor removido do working tree do frontend — presente no último commit, ausente no estado atual não commitado, sem pasta android/. Se o app Android depende de assinatura compartilhada, esclarecer esse estado antes de prometer paridade Web/Android.

14

Ordem recomendada de implementação

1

Correções estruturais de segurança

Rotacionar segredo JWT, corrigir bug de validade do token, unificar CORS, rate limiting no login.

2

Decisão de modelo de conta

Assinatura por usuário (mais simples, compatível com o banco atual) ou por "empresa" (exige nova tabela e migração de dados).

3

Banco de planos e assinaturas

Criar plans, subscriptions, payment_events via changelog Liquibase.

4

EntitlementService no backend

Camada central de checagem de limites, plugada nos controllers existentes (Car, Driver etc.).

5

BillingService + interface PaymentProvider

Sem gateway real ainda — só a abstração e um provider "fake"/sandbox.

6

Integração com um gateway

Asaas ou Mercado Pago primeiro. Checkout hospedado pelo gateway — o Frotto nunca guarda dado de cartão.

7

Webhooks

Rota pública, validação de assinatura, idempotência, persistência de eventos.

8

Frontend de planos

Tela de escolha de plano, redirecionamento para checkout, tela de status de assinatura.

9

Esclarecer situação Android/Capacitor

Decidir se o app mobile volta a existir e como o status de assinatura é compartilhado com a Web.

10

Testes e homologação

Sandbox do gateway, simulação de eventos de webhook.

11

Produção
